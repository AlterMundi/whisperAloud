## WHISP-93 — root-cause analysis

### How "processed" duration is actually computed

`AudioRecorder.stop()` (`audio/recorder.py:493-551`) is the sole owner of the number printed in `"Recording complete: Xs (processed)"`:

1. `raw_audio = np.concatenate(frames_snapshot)` — every chunk the audio callback appended to `self._frames` while state was `RECORDING`. (Logged separately as `"Recorded Xs of audio"` **before** any processing — this line is conspicuously **absent** from all four field-log excerpts in the ticket. That is the single most useful missing data point — see "what would confirm" below.)
2. mono conversion (no-op if already mono).
3. resample to 16000 Hz **only if** `config.sample_rate != 16000` (default is already 16000, so normally a no-op — ruled out below).
4. **`AudioProcessor.trim_silence(audio, 16000, self.config.vad_threshold)`** — the only operation in `stop()` that can shrink the array length. `self.config` here is `AudioConfig` (not `TranscriptionConfig`): `vad_threshold` default `0.02`, a **linear RMS amplitude** gate, completely distinct from `TranscriptionConfig.vad_threshold` (`0.2`, a Silero speech-probability).
5. `self._pipeline.process(audio, 16000)` — highpass → NoiseGate → AGC → Denoiser → PeakLimiter. **None of these change array length** (gate/AGC/limiter only scale gain in place; denoiser returns same-length array). So pipeline stages cannot, by themselves, explain the shrink.
6. `len(processed_audio) / 16000` is what gets logged.

**Conclusion from tracing the code: step 4 (`trim_silence`) is the only place the number can shrink.** This immediately rules out (with code evidence, not speculation):

- **Resampling direction confusion** (ruled out): both directions were considered per the ticket's instruction. 44.1/48kHz-actually-but-interpreted-as-16kHz would *lengthen* perceived duration (more "16kHz" samples than there really are 1x-time-worth of audio) — not observed. The opposite (16kHz samples re-interpreted at a higher nominal rate) would shorten it, but `AudioRecorder` never does a rate-label swap — it resamples via `scipy.signal.resample`/`resample_poly` keyed off `self.config.sample_rate`, which is a fixed int the daemon set at stream-open time, not something PortAudio can silently override out from under the code. **Confirming measurement:** log `self._device.sample_rate` (native device rate) alongside `self.config.sample_rate` (requested) at stream-open time — if they differ and the *raw* "Recorded Xs" number is itself already short/long relative to wall clock, that would indict this path; today neither value is logged, so it cannot currently be distinguished from the field logs alone.
- **Queue overflow / chunk-worker drop** (ruled out for the default faster-whisper engine): `on_processed_chunk` is only wired up when `is_streaming` is `True` (`service/daemon.py:706-714`), i.e. only for the `nemotron-streaming` engine. The field logs' `"Transcription completed in 2.47s, confidence: 41.97%"` message format matches `Transcriber.transcribe_numpy`'s own `logger.info` (`transcriber.py:442-444`), which is the **non-streaming faster-whisper path** — so the chunk-worker queue (and its 5s/2.0s bounded-drop machinery) is provably not in play for these specific log lines.
- **Chunk-worker join timeout** — same reasoning: not reached on this path.
- **NoiseGate/AGC/Denoiser/Limiter "dropping" audio** — ruled out: none of these stages change array length (traced line-by-line above).

### Ranked hypotheses for what actually shrinks it

1. **(Leading hypothesis, HIGH confidence) Energy-based `trim_silence` cutting a quiet/under-boosted recording down to its loudest cluster.** `trim_silence`'s window/threshold logic (`detect_voice_activity`, 25ms window, 10ms hop) finds the *first* and *last* sample index where RMS exceeds the **absolute linear** threshold `0.02`, then slices `[first-100ms, last+100ms]`. If the mic signal's RMS is below `0.02` for most of the recording — plausible under Flatpak, because `GainController.__post_init__` (`service/media_control.py:153-160`) unconditionally sets `self._wpctl = None` inside a Flatpak sandbox (WHISP-61: no `wpctl`, no PipeWire socket access), making `rf.raise_mic_gain` a silent no-op — then only the loudest word/syllable crosses threshold, and the whole rest of the 6s/7s recording gets trimmed away. This exactly matches: a 1.45s remainder out of 6s spoken (one loud phrase recognized at 41.97% confidence — consistent with a short, possibly clipped/isolated fragment of continuous speech), and a 0.24s remainder transcribed as literally "What?" (a single loud interjection). It also explains why trimming is asymmetric/collapses to a small window rather than evenly shortening — `trim_silence` only looks at *first/last* crossing, not a continuous span, so one early loud moment with everything after it below threshold produces exactly this signature.
   - **What would confirm it:** (a) the currently-unlogged `"Recorded Xs of audio"` raw-duration line — if raw ≈ 6s/7s (matching wall clock) and only "processed" shrinks, this hypothesis is confirmed outright; (b) a one-line diagnostic log of the RMS/peak level of `raw_audio` before `trim_silence` runs; (c) confirm in the field whether `GainController._wpctl` was `None` (it always will be under Flatpak — this is deterministic, not probabilistic, per the code) and whether the user's PulseAudio source volume was below whatever level maps to RMS ≥ 0.02 for normal speech.
2. **(Second hypothesis, MEDIUM confidence) Stream cold-start latency under Flatpak's PulseAudio proxy.** `self._start_time = time.time()` (`recorder.py:438`) is captured *before* `sd.InputStream(...).start()` is called and well before the underlying Pulse/Flatpak audio portal has actually begun delivering real (non-silent) callback frames. If opening a *new* Flatpak-sandboxed Pulse connection has multi-second negotiation latency (portal permission re-check, cold sink/source activation), the user could be speaking for several seconds into a stream that isn't capturing yet, and genuinely only ~1-2s of real raw audio accumulates in `self._frames` by the time they stop — in which case `trim_silence` wouldn't even be the culprit, the *raw* buffer itself would already be short. This is **indistinguishable from hypothesis 1 using only the current log lines** — both hypotheses predict a short "processed" number; they diverge only on whether "Recorded Xs of audio" (currently unlogged in the field capture) is also short.
   - **What would confirm it:** same raw-duration log line as above; if raw is already short (≈1.5s/0.25s, not ≈6s/7s), this hypothesis wins over hypothesis 1 and the fix target shifts to stream-open latency (e.g. measure time between `sd.InputStream(...)` construction and the first callback actually firing with non-zero-size `frames`).
3. **(Third hypothesis, LOW-MEDIUM confidence, explains the "No audio frames recorded" case specifically, not the 1.45s/0.24s cases) Hotkey double-fire / rapid toggle.** The `13:12:39` log line ("Recording started ; same second Stopping -> No audio frames recorded") is a qualitatively different failure (zero frames, not "some but short") from the other two cases. This matches a StartRecording immediately followed by a StopRecording within the same wall-clock second — consistent with the class of hotkey-toggle-loop bug the two most recent merged commits (`5a9c711`, `7226553`) targeted. It is plausible (though not proven from these logs alone) that a residual double-activation (one physical keypress producing two `ToggleRecording` D-Bus calls, e.g. via both a `GlobalShortcuts` portal `Activated` signal *and* a stale libkeybinder3 or tray binding still active) could fire start-then-stop before even one `chunk_duration` (0.1s) blocksize of audio has been delivered by PortAudio.
   - **What would confirm it:** add a per-call sequence-number or caller-identity log to `ToggleRecording`/`StartRecording`/`StopRecording` in `daemon.py`, and check whether two D-Bus calls land within the same event-loop tick around `13:12:39`; also check `service/hotkey.py`'s `detect_backend()` output in the daemon's startup log for that session (which backend was actually in use — portal vs libkeybinder3 vs none) and whether more than one was simultaneously registered.
4. **(Ruled out) Config migration mixing up `audio.vad_threshold` (0.02, linear) with `transcription.vad_threshold` (0.2, probability).** The ticket's listed Flatpak config values (`audio_processing.highpass_hz=0.0`, `transcription.highpass_hz=80`, `vad_threshold=0.2`) all match the **current upstream defaults exactly** (`config.py:149,171,287`) — i.e. this looks like an unmodified/correctly-migrated config, not a corrupted one. `config.py`'s `from_dict()` reads strictly from matching nested JSON sections (`data["audio"]`, `data["transcription"]`, `data["audio_processing"]`) via `hasattr` checks, so a flat-key migration bug that cross-wires `audio.vad_threshold` with `transcription.vad_threshold` is not supported by the code as written — there is no shared/flat namespace for these two keys to collide in. Keeping this as a documented "checked and ruled out" item rather than omitting it, since the ticket specifically asked to check it.
